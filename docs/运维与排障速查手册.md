> **适用对象**：接手系统维护的运维工程师、全栈开发者、运营技术负责人。  
> **编写目标**：拿来即用，5 分钟上手部署，覆盖日常高频运维操作与突发故障应急预案。

## 🚀 一、系统极速部署与启动（3 步到位）

### 步骤 1：安装 Python 运行环境
* **要求**：Python 3.9 或更高版本（64位）。
* **安装依赖**：
  ```bash
  cd "项目根目录"
  pip install -r requirements.txt
  ```
  *(注：系统使用了 `curl_cffi` 用于模拟 Chrome 124 TLS 指纹穿透反爬，必须确保成功编译或安装预编译 wheel)*

### 步骤 2：配置环境变量
复制根目录 `.env.example` 为 `.env`：
```bash
copy .env.example .env
```
根据实际情况配置以下必填项：
* `DEEPSEEK_API_KEY` 或 `QWEN_API_KEY`：AI 清洗与质检大模型密钥；
* `DEFAULT_SELLER_ID` 与 `DEFAULT_FK_CSRF_TOKEN`：默认店铺凭据；
* 其他配置项保持默认即可。

### 步骤 3：一键启动系统
* **Windows 环境推荐**：直接双击根目录的 **`启动系统.bat`**。
  * 该批处理会自动启动 `start_system.py`；
  * 自带**局域网 80 端口反向代理**（若 80 被占自动降级 8000/8001），同事在同一局域网下输入您的本机 IP 即可直接免端口访问；
  * 自带崩溃 3 秒自愈重启机制。
* **访问控制台**：浏览器打开 `http://127.0.0.1:8001` 或 `http://localhost:8001`。
* **默认账号密码**：
  * 超级管理员：`admin` / `admin123`
  * 运营员工：`operator1` / `123456`

## 🛠️ 二、核心业务模块与日常运维标准动作

### 1. 智能跟卖 (Piggyback) 与 Buybox 巡检
* **7 大 KPI 看板含义**：
  1. `📦 跟品总池`：系统全量跟品底库总数；
  2. `🟢 在售监控`：已成功在 Makro 官方在售（ACTIVE）且纳入日常改价巡检的商品数；
  3. `💎 独家在售`：前台仅本店 1 家在售、无外部竞对跟卖的商品（全店最稳利润源）；
  4. `🥇 占位赢车`：本店或矩阵兄弟店铺当前报价最低，持有黄金购物车 Buybox；
  5. `🚨 丢车需调价`：外部真实竞对价格更低，需要下调售价抢车；
  6. `🛡️ 底价坚守中`：竞对报价过低已触碰保本底线，系统坚守底价不降，防止亏损；
  7. `⚠️ 缺底价高危`：尚未设置保本底价的在售商品，建议立即批量设置底价。
* **三轨独立重试与防误入待处理池机制**：
  * **挂靠失败**（官方接口报错/需资质）：操作列点击 **`🚀 重新挂靠`**，直接重新调用官方发布网关，**绝不会回退到待处理池重跑爬虫**；
  * **采集失败**（链接失效/404）：操作列点击 **`🔄 重新采集`**，重新推入后台爬虫队列拉取；
  * **在售巡检遇阻**（反爬阻断/官方同步超时）：状态保持在售，行内显示 `⚠️ 巡检遇阻`，点击 **`⚡ 重试跟价`**，直接重新比价调价，绝不掉出在售池。

### 2. 店铺下架与清零库存应急操作（如侵权拦截或弃用）
当运营需要在官方店铺下架某商品并清空库存时：
* 系统已集成 **双重下架保底机制**：
  1. 调用 `create-update-listings` 将官方 `listing_status` 设为 `INACTIVE`；
  2. 联动调用 `updateListingsInventory` 将仓库库存强制清零为 `0`；
  3. 同步修改本地 `makro_listings` 为 `INACTIVE`，将跟卖库移入 `已弃用池 (防重采)`。
* 如需代码直接批量下架，可调用：
  ```python
  from app.services.makro_piggyback_service import MakroPiggybackService
  # 调用 batch_deactivate_piggyback_listings，内置动态代理池，100% 连通官方
  MakroPiggybackService.batch_deactivate_piggyback_listings(items, store, db)
  ```

### 3. 多店铺凭据保活 (Cookie / CSRF)
* **凭据有效期**：Makro 官方 Session Cookie 通常为 24 小时左右。
* **两种保活方式**：
  * **自动化保活**：系统每 21 小时通过后台调度器连接店铺绑定的邮箱（IMAP）接收登录 OTP 验证码完成无感自动登录；
  * **插件手动一键同步**：若自动登录受阻，运营只需在已登录 Makro 卖家后台的 Chrome 页面，点击插件上的【同步登录态至后台】按钮即可秒级刷新。

## 🔍 三、常见故障诊断与排障速查表 (FAQ)

| 故障现象 | 根因排查 | 解决方案与处置标准 |
| :--- | :--- | :--- |
| **页面打开出现白屏** | 公网 CDN（如 unpkg/jsdelivr）加载失败 | 系统已内置本地 `vendor/vue.global.prod.js` 自动降级自愈。若仍有异常，检查浏览器是否拦截了本地 js 资源。 |
| **请求 seller.makro.co.za 报错 Read timed out** | 境内网络直连南非 Makro 官方网关高延迟或被墙 | 系统已在 `makro_piggyback_service` 与 `makro_portal_service` 中接入 `ProxyPoolService.get_proxy()`。检查携趣代理 API 是否已将当前出口 IP 加入白名单。 |
| **刊登或调价报错 403 Forbidden / CSRF Mismatch** | 店铺登录态 Cookie 或 CSRF 令牌过期 | 进入【店铺管理】界面点击【立即测试登录保活】，或使用 Chrome 插件在 Makro 后台点击【一键同步凭据】。 |
| **AI 质检大批量报 429 Too Many Requests** | 大模型厂商突发限流 | 系统已实现 3 次指数退避智能重试（0.8s ➔ 1.6s ➔ 3.2s）。如需长期大批量并发，可调大 `.env` 中的 API 并发阈值或切换至 DeepSeek。 |
| **商品标题质检提示 RISK: 缺少兼容词** | 品牌配件标题未明确包含兼容词汇 | 系统采用“宁可杀错，不可放过”原则。只要是品牌配件，标题中必须明确包含 `for / compatible with / replacement for`，否则强制判定为 `RISK` 阻断刊登。 |
| **SQLite 数据库报错 Database is locked** | 密集多线程并发写冲突 | 系统已启用 WAL 模式。常规操作下会自动排队重试；如果团队扩张，可随时在 `.env` 中无缝将 `DATABASE_URL` 改为 PostgreSQL。 |

## 💾 四、数据库备份与恢复指引

系统默认主数据库位于：`backend/makro_app.db`。

### 1. 手动快速备份
```bash
# 复制当前数据库为带日期的备份文件
copy "backend\makro_app.db" "backend\makro_app_backup_%date:~0,4%%date:~5,2%%date:~8,2%.db"
```

### 2. 数据库迁移自检
系统启动时，`backend/main.py` 和 `backend/app/init_db.py` 会自动扫描缺失的表和列，自动执行增量 `ALTER TABLE` 补齐字段，无需手动执行 alembic 即可平滑升级。

## 📦 五、浏览器插件二次开发与打包

* **插件源代码目录**：`extension/` (Chrome Manifest V3)
* **一键打包命令**：
  ```bash
  python backend/tools/bump_version.py --patch-all
  ```
  执行后会自动同步版本号，并重新编译生成：
  1. 根目录 `extension.zip`
  2. 后端下载目录 `backend/app/static/makro-extension.zip`
* **插件安装方式**：
  在 Chrome 浏览器打开 `chrome://extensions` ➔ 开启【开发者模式】➔ 点击【加载已解压的扩展程序】➔ 选择项目的 `extension` 目录。
