> 本文档专为接手和维护本系统的技术人员编写。请在开始修改代码或部署前仔细阅读本手册。

## 一、系统定位与架构总览

本系统是一套面向南非跨境电商（主攻 **Makro** 卖家平台，货源对齐 **Takealot** 及国内供应链 1688）的自动化运营中台。系统涵盖了：
1. **轻量选品采集**：Takealot 原生 REST API 毫秒级多变体采集 + CSV 批量导入；
2. **AI 清洗与风控**：DeepSeek / 通义千问智能重塑标题、16+ 项类目属性抽取、品牌侵权转兼容、受限品拦截；
3. **协议级批量刊登**：逆向破解 Makro（Flipkart SaaS 底层）草稿、CDN传图、限定符适配、批量提审；
4. **智能跟卖 (Piggyback)**：Makro 前台竞品一键跟卖采集、利润与底价核算；
5. **动态改价巡航**：Chrome 124 TLS 拟真穿透 PerimeterX 反爬、5 并发抖动防护、抢占 BuyBox、底价保护；
6. **无人值守自动化**：多店铺 21 小时定期登录保活、IMAP 邮箱提取 OTP 验证码、30 分钟订单与在售 Listing 静默同步；
7. **多用户与人效审计**：RBAC 权限、操作员工作量统计与任务执行轨迹。

## 三、Makro (Flipkart SaaS) 逆向刊登核心协议解析

Makro 卖家后台基于印度 Flipkart 架构改造，其协议交互具有非常严格的时效和限定符校验规则。

### 1. 认证与凭据机制
- **`seller_id`**：店铺唯一十六进制 ID（例如 `cb80491bf0a34dc5`）。
- **`fk-csrf-token`**：CSRF 防伪令牌，所有 `POST`/`PUT` 请求必须在 Header 中携带。
- **`Cookie`**：包含会话认证凭据。通常有效期为 **24 小时**。
  > **注意**：如果返回 `403 Forbidden` 或 `Invalid CSRF Token`，通常代表凭据过期，需要通过浏览器插件重新同步或由自动登录调度器刷新。

### 2. 商品刊登四步流程链

```
1. 创建草稿 (create_draft)
   POST https://seller.makro.co.za/api/catalog/products/draft
   入参: { vertical: "...", brand: "...", title: "..." }
   返回: { requestId: "...", txnId: "...", draftId: "..." }

2. 图片上传至 Makro CDN (upload_image_to_cdn)
   POST https://seller.makro.co.za/api/catalog/images/upload
   注意: 必须先将 Takealot 原图下载并转存至 Makro 官方 CDN，换取官方 cdnUrl

3. 属性映射与限定符单位自适应 (build_payload)
   Makro CMS 校验极其严格：
   - allowedValues: 枚举值必须一字不差匹配官方定义
   - Qualifier: 如容量需要 qualifier="GB" 或 "TB"，重量需要 qualifier="kg"
   - Model Number: 属性值中严禁包含品牌名 Brand Name

4. 提交平台审核 (submit_product)
   POST https://seller.makro.co.za/api/catalog/products/submit
   入参携带完整 draft 数据包，成功后变体状态变更为 SUBMITTED
```

## 四、智能跟卖与动态改价巡航体系

### 1. PerimeterX 反爬与 TLS 指纹穿透
Makro 前台（`www.makro.co.za`）部署了 PerimeterX / Human Security 反爬防护。普通 `requests` 或 `httpx` 发起请求会直接收到 **403 Access Denied** 或 JS 验证码。
- **解决方案**：系统在 `makro_scraper_service.py` 中使用了 `curl_cffi`，配置 `impersonate="chrome124"`，完整模拟现代 Chrome 浏览器的 TLS Client Hello、JA3 指纹及 HTTP/2 协议特征。
- **请求频次与抖动削峰**：在 `auto_reprice_service.py` 中限制最大并发数为 **5 个线程**，并在每次抓取间添加 **0.3~0.8 秒随机抖动**，防止突发流量引发平台临时 IP 封锁。

### 2. 改价判定逻辑与状态机
在售跟卖商品每 60 分钟自动巡航一次（或由管理员在控制台手动触发全量巡航）：
- **`WINNING` (赢车)**：当前 BuyBox 最优报价即为我方店铺，保持当前售价；
- **`LOSING` (丢车)**：外部竞对占据 BuyBox，系统根据策略（如 `MINUS_1`）自动计算新价格并推送到 Makro 卖家后台，成功后重新夺取 BuyBox；
- **`FLOOR_HIT` (底价保护)**：竞对售价低于我方预设的保底价格（`min_price_floor`），系统立即终止降价并打标，防止负利润价格战；
- **`is_abandoned` (已弃用)**：对于利润空间丧失或不再经营的 SKU，支持一键弃用，自动从巡航比价池中剔除。

## 五、多店铺自动化保活与静默同步

### 1. 21 小时定期登录保活机制 (`auto_login_scheduler.py`)
Makro 登录态有效期约为 24 小时。为实现全自动免人工干预：
1. 后台线程定时检查各店铺的 `last_auto_login_at`；
2. 距上次登录超过 21 小时即触发登录流程；
3. 发起 Makro 登录请求 -> 触发平台向注册邮箱下发 6 位 OTP 验证码；
4. `EmailOTPService` 通过 IMAP 协议连接该店铺绑定的邮箱，拉取最新验证码；
5. 提交 OTP 完成登录，更新数据库中该店铺的最新 `cookie` 与 `fk_csrf_token`。

### 2. 30 分钟订单与 Listing 静默同步 (`order_sync_scheduler.py`)
- 每 30 分钟轮询所有活跃店铺；
- 自动拉取 Makro 卖家中心的待发货订单，更新到 `makro_orders` 表，便于团队及时打单履约；
- 自动同步在售 Listing 的库存与上架状态至 `makro_listings` 表。

## 六、数据库核心数据表字典 (SQLite)

系统使用单文件 SQLite 数据库 `backend/makro_app.db`（支持通过 `DATABASE_URL` 切换 MySQL/PostgreSQL）。

### 1. 选品与刊登核心表
- **`products`**：父商品表
  - `plid`：Takealot 商品唯一标识（带唯一索引）
  - `status`：状态（`PENDING` 待处理 / `CLEANED` 已清洗 / `SUBMITTED` 已刊登 / `FAILED` 失败 / `ABANDONED` 弃用）
  - `clean_mode`：清洗模式（`text` / `vision`）
  - `compliance_status`：合规状态（`SAFE` / `SUSPECT` / `VIOLATION`）
  - `user_id`：归属操作员 ID
- **`product_variants`**：异构变体明细表
  - `product_id`：外键关联 `products.id`
  - `takealot_tsin`：Takealot 变体唯一 TSIN
  - `variant_type`：变体类型（容量 / 尺码 / 颜色 / 包装数）
  - `barcode`：商品条形码 EAN/UPC
  - `images`：该变体专属的高清图组 JSON
  - `makro_sku_id`：Makro 平台生成的唯一 SKU

### 2. 多店铺与权限核心表
- **`stores`**：店铺配置表
  - `name` / `seller_id` / `fk_csrf_token` / `cookie`
  - `login_email` / `login_password` / `imap_server` / `imap_user` / `imap_password`：自动保活参数
  - `last_auto_login_at` / `last_auto_login_status`：保活状态追踪
- **`product_store_listings`**：商品与店铺发布关联表（支持同一商品发布到多个店铺）
- **`users`** & **`user_stores`**：RBAC 权限体系
  - `role`：`ADMIN`（管理员） / `OPERATOR`（操作员）
  - `user_stores`：操作员可管理的店铺权限绑定关系
- **`task_logs`**：操作流水与任务审计日志（记录操作员、动作类型、成功/失败数量）

### 3. 跟卖与改价核心表
- **`makro_piggyback_items`**：跟卖池
  - `store_id`：所属店铺
  - `seller_sku`：我方上架 SKU
  - `makro_product_id` / `item_id`：Makro 平台商品标识
  - `target_price` / `target_mrp`：当前我方报价
  - `min_price_floor`：底价保护红线
  - `max_price_ceiling`：最高售价限额
  - `auto_reprice`：自动改价巡航开关
  - `buybox_status`：`WINNING` / `LOSING` / `FLOOR_HIT`
  - `is_abandoned`：是否弃用
- **`makro_reprice_logs`**：改价流水记录表
  - 记录每次改价事件：竞对卖家名称、竞对价格、我方旧价格、我方新价格、触发原因、执行动作

## 八、常见故障与排错 FAQ

### Q1: 刊登或跟卖时提示 403 Forbidden / CSRF Token Expired？
- **原因**：Makro 卖家 Cookie 或 CSRF Token 过期。
- **解决**：
  1. 打开已登录 Makro 卖家后台的 Chrome 标签页，点击插件中的【同步登录态至后台】；
  2. 或在系统控制台的【店铺管理】中检查该店铺是否配置了正确的邮箱与 IMAP 参数，点击【立即测试登录保活】由系统全自动刷新。

### Q2: 改价巡航抓取 Makro 前台时偶现 403 / 验证码？
- **原因**：受 Makro 前台 PerimeterX 防爬系统识别。
- **检查项**：
  1. 确保 Python 环境已正确安装 `curl_cffi`（`pip install curl_cffi>=0.7.0`）；
  2. 巡航并发建议保持在 5 以内，避免调大并发线程；
  3. 系统已内置随机请求抖动与重试机制，少量个别 SKU 偶发错误属于正常现象，下次巡航周期将自动补齐。

### Q3: 变体发布报错 "Invalid attribute qualifier" 或 "Allowed value mismatch"？
- **原因**：Makro 平台针对不同 Vertical 类目的属性值和单位限定符规则变动。
- **解决**：
  1. 查阅 `backend/app/services/makro_verticals.json` 中该类目的定义；
  2. 在 `backend/app/services/vertical_service.py` 中补充单位限定符（如 `GB/TB`, `kg/g`）的映射转换字典；
  3. 在控制台审品页面手动微调该属性后重新提交。

### Q4: 提示 SQLite Database is locked？
- **原因**：后台定时同步线程与前台并发写操作冲突。
- **解决**：
  1. 系统已启用 WAL（Write-Ahead Logging）模式优化；
  2. 所有高频查询已在 `main.py` 启动阶段建立了复合索引；
  3. 如在大型多团队协作生产环境，建议将 `.env` 中的 `DATABASE_URL` 无缝切换至 PostgreSQL。
